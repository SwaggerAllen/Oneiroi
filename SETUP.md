# Setup

The attended runbook for standing an instance up: the human steps P0.5
leaves (`design/p0-plan.md`), one-time, in order, because values made
early are consumed late. Everything code-shaped is in the tree: the
Dockerfile and `render.yaml`, `pipeline.config.json` with the tracker
ids and the gate set, the twelve pipeline stubs under
`.github/workflows/`, `ci.yml` with its self-arming pipeline audit, and
the design artifacts (`systems/`, `screens/`, `CHANGE.md`,
`non-asks.md`, `tests/manual/`).

## Required variables this codebase invented

The block below is read by `mix oneiroi.audit`: every variable this
codebase requires with no default and no external name is listed here,
one per line, or the audit says so, and a line no declaration explains
is reported too. Names only; where each goes is in the steps below.

```oneiroi:required-env
APSU_SECRET_KEY_BASE   # the endpoint's cookie-signing secret, 64 bytes or more
APSU_VAULT_KEY         # 32 random bytes, base64: what secrets at rest are encrypted under
```

`DATABASE_URL` and `RENDER_EXTERNAL_URL` are deliberately absent: both
are declared `external: true` because Render supplies them under names
this codebase does not choose. `render.yaml` binds the first from the
database; Render sets the second on every web service, previews
included, to the service's own origin, and the endpoint answers as it
(`systems/apsu.md` #19). A self-hosted instance sets both by hand.

## 1. The reference instance (Render)

`render.yaml` is the service's shape: a Blueprint Render creates the
services from and re-reads on every push. The dashboard is the
authority on everything the Blueprint does not set, which is every
secret (`sync: false`).

The service carries a persistent disk, `oneiroi-records`, at
`/var/lib/oneiroi` (sima-qian #23): every resident's working repository
lives there, and without it a deploy replaces them. Before an import,
check the service's Disks tab shows it mounted.

1. Create the Blueprint from `render.yaml`, pointed at this branch until
   it merges. **Read the Postgres major Render offers with pgvector off
   the dashboard** and, if it is not 16, change `postgresMajorVersion`
   in `render.yaml` and the `pgvector/pgvector:pg16` image in `ci.yml`
   and the five stubs that carry it, in one commit (plan decision 3).
2. The two secrets above are generated by Render (`generateValue` in
   `render.yaml`), once per service, so production and every preview
   hold their own and nobody types a key. A value already set in the
   dashboard is kept. To set one by hand instead: `APSU_SECRET_KEY_BASE`
   is 64 or more bytes (`mix phx.gen.secret 64`) or base64 of 32 or
   more, and `APSU_VAULT_KEY` is base64 of exactly 32 bytes (`openssl
   rand -base64 32`). A deploy without either fails at boot with the
   config report naming it.
3. Read the service id (`srv-…`) and set it as the `RENDER_SERVICE_ID`
   secret in §4: `pipeline.config.json`'s `deploy.endpoint` is
   `https://api.render.com/v1/services/${RENDER_SERVICE_ID}/deploys`.
   Unset, every `pipeline` command fails at config load naming it, and
   `pipeline setup`'s deploy probe is what checks the id is the right
   one, which is why that probe runs at hookup rather than on the first
   ticket to reach `Merged`.
4. Two things to read off the first deploy and write into the plan's
   measurement table: the database's connection limit against
   `APSU_POOL_SIZE` and `APSU_EVENT_STORE_POOL_SIZE` (both
   default 2, Catapult's budget against a 22-connection cluster; the Repo, the event store's pool, and one listener each
   for Oban and the store share the limit, and a rolling deploy runs two
   containers), and whether a preview environment can take a smaller
   database plan than production.
5. Run the one account's creation once the service answers `/health`,
   from a shell on the service (the Render shell, or SSH as user
   `srv-…` to `ssh.<region>.render.com` with a key added under Account
   Settings → SSH Public Keys). The image is an OTP release with no Mix
   in it, so `mix oneiroi.setup` exists only in a checkout; on the
   service, the release calls the same function on the running node:

   ```sh
   /app/bin/oneiroi rpc 'IO.inspect(Oneiroi.Gaia.create_account("<you>", "<password>", Oneiroi.Actor.platform()))'
   ```

   It prints `{:ok, <account id>}`; clear the shell's history after,
   since the password is in it. Autodeploy stays on; the image's own
   `CMD` runs the migrator ahead of `start`, so a failed migration fails
   the deploy with the previous one still serving.
6. Honcho (spec §6.9, proteus #16 and #17) comes with the Blueprint:
   the private `honcho-api` and the `honcho-deriver` worker, built from
   `plastic-labs/honcho`'s own Dockerfile, on `oneiroi-db` in a schema of
   their own under the role `oneiroi_honcho`, which Oneiroi's migration
   creates. Deploy Oneiroi first so that migration has run: until it
   has, Honcho's connection names a role that does not exist and its
   deploy fails. One value is yours to set by hand, in the dashboard:
   `LLM_OPENAI_API_KEY` on `honcho-api`, **your OpenRouter key**, the same
   one stored on your account and in the `OPENROUTER_API_KEY` secret the
   fixture run reads. Render prompts for a `sync: false` value only when a
   Blueprint is first created, so a sync that adds one to an existing
   Blueprint leaves it empty and asks nothing (the first Honcho deploy,
   10-31). The deriver copies it, and every Honcho feature
   (embeddings, derivation, the dialectic, summaries, dreams) is routed
   to OpenRouter by the `honcho` environment group. Everything else is
   wired: Render generates `AUTH_JWT_SECRET`, the core mints the admin
   key from it, and `PROTEUS_HONCHO_URL` is `honcho-api`'s private
   address. Neither Honcho service deploys on its own
   (`autoDeployTrigger: off`): the first deploy takes upstream `main` as
   it is that day, so read its version off the build log, and a later
   upgrade is a manual deploy after reading the release notes. Check with
   the Honcho page on the resident's screen (`GET /v1/residents/:id/honcho`):
   a sync recorded as `ok` after a turn is the bridge working end to end.

## 3. The tracker

The Linear project exists: **Oneiroi** under the `ORC` team; its id
and the team's are the `LINEAR_PROJECT_ID` and `LINEAR_TEAM_ID`
variables below, which `pipeline.config.json`'s `tracker` block names as
`${…}` references. Run `pipeline-admin` with `setup`, dry first and
then applied, to create any state or label the team lacks; the state
names are the config's `states` map.

## 4. Secrets, webhook, repo settings (GitHub UI)

Actions secrets the config reads (Settings → Secrets and variables →
Actions → Secrets); the config names each as a `${…}` reference
(orchestration's DESIGN §5), the twelve stubs and `ci.yml` hand them
over in one `env:` block, and a `pipeline` command run with one unset
fails naming it. Secrets rather than variables, though none is a
credential, because a public repository's run logs print each step's
environment and mask only secrets:

- `PIPELINE_STATE_URL`: the metronome Worker's origin,
  `https://pipeline-metronome.<subdomain>.workers.dev`.
- `LINEAR_TEAM_ID` and `LINEAR_PROJECT_ID`: the `ORC` team and the
  Oneiroi project.
- `LINEAR_AUTHOR_ID`: your Linear user id, the config's `author` and
  `controlplane` actor.
- `RENDER_SERVICE_ID`: the reference instance's `srv-…` id from §1.

Actions secrets the workflows read directly:

- `LINEAR_API_KEY`
- A model credential: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude
  setup-token`, tried first) and/or `ANTHROPIC_API_KEY` (the failover);
  at least one.
- `PIPELINE_REPO_TOKEN`: Contents read on the orchestration repo. Until
  it exists, `ci.yml`'s pipeline audit step prints "skipped" on every
  run, and a clean run on an author branch is not evidence it passed.
- `AGENT_GITHUB_TOKEN`, with this repo on its repository list; without
  it agents fall back to `GITHUB_TOKEN` and degrade loudly (CI never
  triggers on agent pushes, deploys are not recorded, bot PRs wait for
  manual approval).
- `RENDER_API_KEY`: reads only; deploy detection is one GET against the
  service's deploys.
- `PIPELINE_STATE_TOKEN`, matching the metronome Worker's `STATE_TOKEN`:
  the pipeline's record of its own writes, without which it judges
  nothing and says so on every sweep.
- `STATS_GITHUB_TOKEN`: a fine-grained PAT with Actions read on this repo
  and on orchestration, for `pipeline-stats` alone.

Then: the GitHub webhook on this repo to the Worker URL (content type
JSON, the orchestration repo's `WEBHOOK_SECRET`, events **Workflow runs**
and **Deployment statuses**; without it every CI hop waits for the
hourly cron); Settings → Actions → General → allow GitHub Actions to
create and approve pull requests; branch protection on `main` requiring
the `ci` check and pull requests, your own pushes as the deliberate admin
bypass. The repo variable `PIPELINE_KILL_SWITCH=true` parks the
project; clear it before expecting any work.

Run `pipeline-preflight` once everything above is set: it exercises
every credential-bearing read and names the write scopes it did not.

## 5. Verification (P0.5's exit)

File the verification ticket (a README touch) in the Oneiroi project
and move it to **Designing**: starting work is always the author's act.
Watch it flow design → dev → reconcile → deploy unattended. Its `Done`
is the exit, and the moment the ci audit step stops printing "skipped".
From there the backlog holds P1 as coarse placeholders; P0.6 and P0.7
were built attended with the spine (decisions log round 9), so the
plan's drafts for them become follow-ups rather than the first work.

## 6. The records run by hand (P0's exit)

Once a resident exists: `PUT /v1/residents/:id/remote` with a GitHub
repository you created and a fine-grained token scoped to it (Contents
read and write), then the backup from a shell on the service through
the release (`/app/bin/oneiroi rpc 'IO.inspect(Oneiroi.SimaQian.backup(<resident id>, Oneiroi.Actor.platform()))'`,
as in §1 step 5), read the
`Oneiroi-Sequence` and `Oneiroi-Root` trailers off the commit on GitHub,
and `mix oneiroi.sima_qian.rebuild <repo> --witness <account id>` against
a second database. The export of the rebuilt resident is byte-identical
up to the `Imported` line; the test suite asserts the same against a
local bare repository on every PR.
