# Setup

The attended runbook for standing an instance up: the human steps P0.5
leaves (`design/p0-plan.md`), one-time, in order, because values made
early are consumed late. Everything code-shaped is in the tree: the
Dockerfile and `render.yaml`, `pipeline.config.json` with the tracker
ids and the gate set, the twelve pipeline stubs under
`.github/workflows/`, `ci.yml` with its self-arming pipeline audit, and
the design artifacts (`systems/`, `screens/`, `CHANGE.md`,
`non-asks.md`, `tests/manual/`).

## Required variables this codebase invented

The block below is read by `mix oneiroi.audit`: every variable this
codebase requires with no default and no external name is listed here,
one per line, or the audit says so, and a line no declaration explains
is reported too. Names only; where each goes is in the steps below.

```oneiroi:required-env
APSU_SECRET_KEY_BASE   # the endpoint's cookie-signing secret, 64 bytes or more
APSU_VAULT_KEY         # 32 random bytes, base64: what secrets at rest are encrypted under
```

`DATABASE_URL` and `RENDER_EXTERNAL_URL` are deliberately absent: both
are declared `external: true` because Render supplies them under names
this codebase does not choose. `render.yaml` binds the first from the
database; Render sets the second on every web service, previews
included, to the service's own origin, and the endpoint answers as it
(`systems/apsu.md` #19). A self-hosted instance sets both by hand.

## 1. The reference instance (Render)

`render.yaml` is the service's shape: a Blueprint Render creates the
services from and re-reads on every push. The dashboard is the
authority on everything the Blueprint does not set, which is every
secret (`sync: false`).

The service carries a persistent disk, `oneiroi-records`, at
`/var/lib/oneiroi` (sima-qian#23): every resident's working repository
lives there, and without it a deploy replaces them. Before an import,
check the service's Disks tab shows it mounted.

1. Create the Blueprint from `render.yaml`, pointed at this branch until
   it merges. **Read the Postgres major Render offers with pgvector off
   the dashboard** and, if it is not 16, change `postgresMajorVersion`
   in `render.yaml` and the `pgvector/pgvector:pg16` image in `ci.yml`
   and the five stubs that carry it, in one commit (plan decision 3).
2. The two secrets above are generated by Render (`generateValue` in
   `render.yaml`), once per service, so production and every preview
   hold their own and nobody types a key. A value already set in the
   dashboard is kept. To set one by hand instead: `APSU_SECRET_KEY_BASE`
   is 64 or more bytes (`mix phx.gen.secret 64`) or base64 of 32 or
   more, and `APSU_VAULT_KEY` is base64 of exactly 32 bytes (`openssl
   rand -base64 32`). A deploy without either fails at boot with the
   config report naming it.
3. Read the service id (`srv-…`) and set it as the `RENDER_SERVICE_ID`
   secret in §4: `pipeline.config.json`'s `deploy.endpoint` is
   `https://api.render.com/v1/services/${RENDER_SERVICE_ID}/deploys`.
   Unset, every `pipeline` command fails at config load naming it, and
   `pipeline setup`'s deploy probe is what checks the id is the right
   one, which is why that probe runs at hookup rather than on the first
   ticket to reach `Merged`.
4. Two things to read off the first deploy and write into the plan's
   measurement table: the database's connection limit against
   `APSU_POOL_SIZE` and `APSU_EVENT_STORE_POOL_SIZE` (both
   default 2, Catapult's budget against a 22-connection cluster; the Repo, the event store's pool, and one listener each
   for Oban and the store share the limit, and a rolling deploy runs two
   containers), and whether a preview environment can take a smaller
   database plan than production.
5. Run the one account's creation once the service answers `/health`,
   from a shell on the service (the Render shell, or SSH as user
   `srv-…` to `ssh.<region>.render.com` with a key added under Account
   Settings → SSH Public Keys). The image is an OTP release with no Mix
   in it, so `mix oneiroi.setup` exists only in a checkout; on the
   service, the release calls the same function on the running node:

   ```sh
   /app/bin/oneiroi rpc 'IO.inspect(Oneiroi.Gaia.create_account("<you>", "<password>", Oneiroi.Actor.platform()))'
   ```

   It prints `{:ok, <account id>}`; clear the shell's history after,
   since the password is in it. Autodeploy stays on; the image's own
   `CMD` runs the migrator ahead of `start`, so a failed migration fails
   the deploy with the previous one still serving.
6. Honcho is retired (proteus#20, 2026-11-18): Oneiroi no longer
   calls it, and sets no `PROTEUS_*` variable. The `honcho-api` and
   `honcho-deriver` services are off the blueprint (proteus#21,
   2026-11-21); taking a service off a blueprint does not delete it on
   Render, so each is deleted from the dashboard. The `oneiroi_honcho`
   role and `honcho` schema still stand until they are removed on the
   witness's word; a new deploy needs none of them.

### Metrics and Grafana (apsu#25)

1. On grafana.com, a free Grafana Cloud stack. Under Connections, add
   the **Metrics Endpoint** integration: scrape URL
   `https://<service>.onrender.com/metrics`, authentication **Bearer**,
   with a long random token. Set the same token on the Render service as
   `APSU_METRICS_TOKEN`. Until it is set, `/metrics` answers 404.
2. For the dashboards: in the stack, a service account with the Editor
   role and a token for it. Set `APSU_GRAFANA_URL`
   (`https://<stack>.grafana.net`) and `APSU_GRAFANA_TOKEN` on the
   service; the next boot uploads PromEx's dashboards and "Oneiroi ·
   where the time goes" to an Oneiroi folder and marks each deploy. Each
   boot overwrites them, so a fix made by hand in Grafana does not last:
   the upload carries the hosted stack's (apsu#33). The datasource is
   named by uid, `APSU_GRAFANA_DATASOURCE` (default `grafanacloud-prom`,
   every Grafana Cloud stack's; its display name, like
   `grafanacloud-<stack>-prom`, will not do), and the shortest rate
   interval is `APSU_GRAFANA_INTERVAL` (default `4m`, twice the Metrics
   Endpoint's 2-minute scrape; change both together).
3. The slow calls themselves, with what they spent their time on and the
   events they dispatched: `GET /v1/ops/spans` and
   `GET /v1/ops/spans/summary` as a super admin (apsu#28).

### Payments: Stripe (nisaba#23)

$20 a month per resident, paid on Stripe's own pages. Unset, checkout
and the card page answer "payments are not set up" and every webhook is
refused; nothing else changes.

1. In the Stripe dashboard (test mode first), Developers → API keys:
   the secret key (`sk_test_…`) as `NISABA_STRIPE_SECRET_KEY` on the
   service. No product or price to make: checkout gives the price inline
   (`NISABA_PLAN_PRICE_CENTS`, 2000 by default).
2. Developers → Webhooks → Add endpoint:
   `https://<the service>/v1/billing/stripe`, with the events
   **checkout.session.completed**, **invoice.paid** and
   **customer.subscription.deleted** (others are answered and ignored).
   Its signing secret (`whsec_…`) as `NISABA_STRIPE_WEBHOOK_SECRET`.
3. Settings → Billing → Customer portal: turn it on, allowing the card
   to be updated, invoices to be seen, and the subscription to be
   cancelled. Without it the client's "Card, invoices and cancelling"
   link is refused by Stripe.
4. A test card (4242 4242 4242 4242) on Settings → Ledger → Subscribe
   should end with the subscription active and paid; the event appears
   under the endpoint in the dashboard with a 200.

Live mode is the same three steps with the live key and a live endpoint.

### Gitea, the repositories' server (sima-qian#55, #57 to #60)

The Blueprint makes `oneiroi-git`: Gitea's official image, its records on
Oneiroi's database (the `gitea` schema as the role `oneiroi_gitea`, which
the migrations make), its git objects on its own 10 GB disk, sign-up off.
Once switched on, Gitea is the source of truth for every repository: the
core reads and writes through its API and refuses writes while it does
not answer. Until the switch (step 4) the core keeps using the records
disk, so nothing is half-moved.

1. On `oneiroi-git` in the dashboard, set `GITEA__server__ROOT_URL` to
   its own URL with a trailing slash (`https://oneiroi-git.onrender.com/`,
   or the name Render gave it) and deploy it once. `/api/healthz` should
   pass.
2. The admin, from the service's Shell tab (the login must be
   `oneiroi-admin`, or set `SIMA_QIAN_GITEA_ADMIN` to the one you use):
   `su git -c "gitea admin user create --admin --username oneiroi-admin --email admin@oneiroi.invalid --random-password --must-change-password=false"`
   (keep the password it prints, in your password manager), then its
   token:
   `su git -c "gitea admin user generate-access-token --username oneiroi-admin --token-name oneiroi --scopes all --raw"`.
3. The push webhook (sima-qian#59), signed in to Gitea as the admin:
   Site Administration → Integrations → System Webhooks → Add Webhook →
   Gitea. Target URL `https://<the oneiroi service>/v1/repos/gitea`,
   method POST, content type `application/json`, a long random secret,
   trigger on push events, branch filter `main`. The same secret goes in
   `SIMA_QIAN_GITEA_WEBHOOK_SECRET` below.
4. On the `oneiroi` service, all at once: `SIMA_QIAN_GITEA_URL` to the
   same URL without the trailing slash, `SIMA_QIAN_GITEA_TOKEN` to the
   token, `SIMA_QIAN_GITEA_WEBHOOK_SECRET` to the webhook's secret, and
   `SIMA_QIAN_REPOS` to `gitea`. The deploy that follows moves every
   repository on the records disk to Gitea, history and all, before
   taking a write (sima-qian#58); its log says `gitea: moved N of N`. An
   organization `h-…` per household appears in Gitea, holding `house`
   and each resident's repository by slug.
5. Check one resident's history on Gitea against the records disk
   (`git log` in the service's Shell under `/var/lib/oneiroi/sima_qian/<id>`);
   once every repository is there, the `oneiroi-records` disk can be
   removed from `render.yaml` in a commit of its own, which lets the app
   run as more than one instance. Until then a restart sends only what
   was not sent.
6. In the client, Settings → Backups, imports and reports → "Your
   repositories on Gitea": set a password, then sign in to Gitea as the
   `w-…` user it names.

## 4. Secrets, webhook, repo settings (GitHub UI)

Actions secrets the config reads (Settings → Secrets and variables →
Actions → Secrets); the config names each as a `${…}` reference
(orchestration's DESIGN §5), the twelve stubs and `ci.yml` hand them
over in one `env:` block, and a `pipeline` command run with one unset
fails naming it. Secrets rather than variables, though none is a
credential, because a public repository's run logs print each step's
environment and mask only secrets:

- `PIPELINE_STATE_URL`: the metronome Worker's origin,
  `https://pipeline-metronome.<subdomain>.workers.dev`.
- `LINEAR_TEAM_ID` and `LINEAR_PROJECT_ID`: the `ORC` team and the
  Oneiroi project.
- `LINEAR_AUTHOR_ID`: your Linear user id, the config's `author` and
  `controlplane` actor.
- `RENDER_SERVICE_ID`: the reference instance's `srv-…` id from §1.

Actions secrets the workflows read directly:

- `LINEAR_API_KEY`
- A model credential: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude
  setup-token`, tried first) and/or `ANTHROPIC_API_KEY` (the failover);
  at least one.
- `PIPELINE_REPO_TOKEN`: Contents read on the orchestration repo. Until
  it exists, `ci.yml`'s pipeline audit step prints "skipped" on every
  run, and a clean run on an author branch is not evidence it passed.
- `AGENT_GITHUB_TOKEN`, with this repo on its repository list; without
  it agents fall back to `GITHUB_TOKEN` and degrade loudly (CI never
  triggers on agent pushes, deploys are not recorded, bot PRs wait for
  manual approval).
- `RENDER_API_KEY`: reads only; deploy detection is one GET against the
  service's deploys.
- `PIPELINE_STATE_TOKEN`, matching the metronome Worker's `STATE_TOKEN`:
  the pipeline's record of its own writes, without which it judges
  nothing and says so on every sweep.
- `STATS_GITHUB_TOKEN`: a fine-grained PAT with Actions read on this repo
  and on orchestration, for `pipeline-stats` alone.

Then: the GitHub webhook on this repo to the Worker URL (content type
JSON, the orchestration repo's `WEBHOOK_SECRET`, events **Workflow runs**
and **Deployment statuses**; without it every CI hop waits for the
hourly cron); Settings → Actions → General → allow GitHub Actions to
create and approve pull requests; branch protection on `main` requiring
the `ci` check and pull requests, your own pushes as the deliberate admin
bypass. The repo variable `PIPELINE_KILL_SWITCH=true` parks the
project; clear it before expecting any work.

Run `pipeline-preflight` once everything above is set: it exercises
every credential-bearing read and names the write scopes it did not.

## 6. The records run by hand (P0's exit)

Once a resident exists: `PUT /v1/residents/:id/remote` with a GitHub
repository you created and a fine-grained token scoped to it (Contents
read and write), then the backup from a shell on the service through
the release (`/app/bin/oneiroi rpc 'IO.inspect(Oneiroi.SimaQian.backup(<resident id>, Oneiroi.Actor.platform()))'`,
as in §1 step 5), read the
`Oneiroi-Sequence` and `Oneiroi-Root` trailers off the commit on GitHub,

up to the `Imported` line; the test suite asserts the same against a
local bare repository on every PR.

## 7. A local app server

For trying the client against a real server on your own machine:
`bin/dev up`, then <http://localhost:4000/client/index.html>, signed in
as `dev@oneiroi.local` / `oneiroi-dev-password`. The script:

- starts the Postgres container (`oneiroi-pg`, Postgres 16 with
  pgvector, user and password `oneiroi`, port 5432; Docker Desktop has
  to be running), migrates `oneiroi_dev`, and seeds it
  (`mix oneiroi.dev.seed`): that account and one resident, Wren, whose
  conversation already holds a long paragraph, a code block with a line
  far wider than a phone, a wide table, an unbreakable word and a system
  line with a long link, plus a day of journal entries, documents in
  three folders, two empty work sessions and three asks in the bell,
  and a household with a second resident, Iris, and a third, Fen, who
  can join the beat running (a contract both have
  signed, a thread both write in, Wren watching it, an open ballot);
- builds the client into the server and rebuilds it on every save
  (reload the page to see a change);
- runs the server on the in-memory provider, which answers each message
  by repeating it and spends nothing. `bin/dev up --live` uses
  OpenRouter instead, on the key stored for the account, and spends.
  The provider is fixed when the code compiles, so the in-memory server
  builds into `_build/dev_fake` and switching recompiles neither.

`bin/dev status` says what runs, `bin/dev logs` follows the server,
`bin/dev down` stops it, and `bin/dev reset` drops `oneiroi_dev` and
starts again from the seed. The seed refuses any database whose name
does not end in `_dev`, and nothing here reaches a deployment. Logs and
process ids are under `tmp/dev/`.

Keep the checkout out of a synced folder. iCloud's Desktop and
Documents sync made " 2" copies of 450 files in this tree on
2026-11-07, and the copied Elixir modules broke the local compile.
