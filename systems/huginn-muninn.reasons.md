# huginn-muninn: reasons

## #8
A counter and a countdown have the same lifecycle (cited, tagged, rendered live) and differed only in where the value comes from; one kind keeps the number rule resolving against one place.

## #9
Spec §6.13: "a counter's value is the fold of its increment events,
each with its actor, from a tool or the steward (the concession-count
pattern)"; F57: "never as a literal in a file."

## #10
Spec §6.7: "a countdown is never written down"; §6.13: "a countdown's
value is derived from a date; both render fresh in the index, both are
citeable." A second row for a countdown would be the stale copy the
rule forbids.

## #11
Spec §6.13: "user-authored audits... read the reference graph, the
audit log and the modification logs, never transcript text"; "each
audit declares whether it counts toward the check-engine light"; "the
coherence work ships as a runnable checklist first."

## #12
Spec §6.13: "each audit run records a result with a tone"; "the
light's findings list is the failing results of the audits that
count"; "results are private to the dyad unless opted in; never a
leaderboard."

## #13
Spec §8: `figure_*` in the brain's tool table; §6.13: counters are
steward-defined keys.
